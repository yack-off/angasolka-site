# Правила разработки Ангасолки

- Основной проект здесь. `public/` — рабочий фронтенд; не менять исходники другой задачи.
- TypeScript strict, Fastify, PostgreSQL. Сохранять модульный монолит; новые каналы используют общие прикладные операции.
- Перед правкой прочитать README.md и docs/architecture.md. Изменять один понятный сценарий, самостоятельно решать рутинные вопросы в рамках запроса.
- Деньги — целые копейки; календарь — Asia/Irkutsk; даты проживания [arrival, departure). Тарифы и свободные места не выдумывать.
- Не доверять цене, роли, источнику, статусу из публичного запроса. Все входы валидировать. SQL только с параметрами.
- Контакты и непроверенные телефоны не являются авторизацией. Секреты и контакты не писать в логи, URL или фикстуры.
- Создание/изменение заказа, аудит и outbox выполнять транзакционно. Сохранять идемпотентность и снимок цены.
- Схему менять новой нумерованной миграцией с обновлением runner; применённую миграцию не переписывать. Production-миграции выполнять явно.
- После backend-изменений выполнить pnpm check и релевантные pnpm test. Для конкурентного инвентаря тестировать реальный PostgreSQL. Проверки должны ловить реальные нарушения, а не повторять реализацию.
- Для изменений формы проверить браузерный путь. После успешных проверок не расширять работу без новых оснований.
- При запросе тестирования обращаться к `docs/testing/README.md`: там тест-кейсы и чек-листы фронтенда, бэкенда и админки/CRM. Результаты каждого прогона сохранять отдельно в `docs/testing/runs/` по шаблону; невыполненные проверки не считать пройденными.
- Обновлять OpenAPI и документацию вместе с API. В отчёте отличать реализованное от будущих шагов и непроверенного.
- Публикация, платежи, сообщения гостям и внешние AI-запросы не следуют автоматически из локальной разработки.
- Постоянный бэклог дефектов — `docs/backlog/README.md`. Сообщения пользователя о дефектах сохранять там, распределять по областям, самостоятельно назначать приоритет и критичность с обоснованием. Сообщение о дефекте означает регистрацию; исправлять по запросу на исправление.
- Перед запросами вроде «исправь фронт», «исправь бэкенд», «исправь админку» читать бэклог и выполнять открытые дефекты соответствующей области по приоритету с учётом зависимостей, последовательно по сценариям. После каждого исправления обновлять карточку: изменения, проверки, статус и дату. Закрывать только после успешной релевантной проверки; непроверенное оставлять в статусе «На проверке». Закрытые карточки сохранять, при повторении проблемы переоткрывать.
