# CRM Ангасолки: выбор подхода и первый рабочий сценарий

Гостинице нужны и CRM (общение и следующие действия), и PMS (размещение, доступность, заезд и выезд). Универсальная воронка сама по себе не предотвращает двойное бронирование.

Решение для текущего проекта: встроенный модуль обработки заявок поверх существующих заказов. Он не требует передачи контактов поставщику, повторного расчёта цены или покупки подписки. Код сторонних продуктов не копировался; внешние аккаунты, API и платные сервисы не подключались.

## Реализовано

В `/admin/` появился пункт **CRM · Гости**. Все существующие и новые заявки доступны автоматически, отдельного импорта нет.

1. Воронка использует общие статусы заявки: «Ожидает связи», «Связались», «Отменена». Из карточки кнопка «Статус и расчёт» открывает существующий редактор. Отмена остаётся окончательной.
2. У заявки есть ответственный из действующих владельцев и менеджеров. Назначение проверяет ту же `orders.version`, что и изменение статуса. Отключённый сотрудник остаётся виден в истории; назначения автоматически не перекидываются.
3. Фильтры: вся команда / мои заявки / без ответственного; просроченные / сегодня / без открытых задач; статус. «Мои» относится к ответственному заявки, а не исполнителю отдельной задачи. Счётчики — по всему выбранному фильтру, страница содержит максимум 25 карточек, распределённых по колонкам.
4. Задачи привязаны к заявке: название, исполнитель, день срока, выполнение и возобновление. Срок — до конца дня Asia/Irkutsk; задача просрочена со следующего местного дня. Разрешены прошлые даты для фиксации уже просроченной работы. Отмена заявки не скрывает и не закрывает задачи автоматически.
5. Внутренние заметки сохраняют автора и дату. Показываются как текст, HTML не выполняется. Заметки не перезаписываются; исправление можно добавить следующей записью. История заметок и задач имеет отдельную пагинацию по 25 записей.
6. Viewer читает; manager и owner работают с CRM. Исполнителем задачи может быть другой действующий manager/owner. Фильтр «Мои» не является ограничением доступа к другим заявкам: модель прав остаётся общей для сотрудников объекта.

Карточка относится к конкретной заявке. Автоматического объединения гостей по непроверенному телефону и межзаявочного профиля гостя пока нет.

## API и данные

Контракт OpenAPI формируется из схем маршрутов: `/api/v1/openapi.json`, тег `CRM`. Все пути ниже начинаются с `/api/v1/admin`, требуют действующую staffSession; изменяющие запросы дополнительно требуют корректный `Origin`.

| Метод / путь | Назначение |
|---|---|
| `GET /crm/team` | Список сотрудников с id, логином, ролью и активностью для назначения; без паролей и сессий |
| `GET /crm/orders` | Воронка: `page`, `assignee=all/mine/unassigned`, `attention=all/overdue/today/no_tasks`, необязательный `status` |
| `GET /crm/orders/:id` | Заметки, задачи и их счётчики; `notesPage`, `tasksPage` |
| `PATCH /crm/orders/:id/assignee` | `{version, assigneeId}`; `null` снимает назначение |
| `POST /crm/orders/:id/notes` | `{id, body}`; UUID операции и до 2000 символов текста |
| `POST /crm/orders/:id/tasks` | `{id, title, assigneeId, dueDate}`; UUID операции, до 200 символов, день `YYYY-MM-DD` |
| `PATCH /crm/tasks/:id` | `{version, status: "open" / "done"}` |

Новая миграция **003_crm.sql**: `orders.assignee_id`, `crm_notes`, `crm_tasks` и индексы. Старые миграции не изменены. Runner применяет третью миграцию один раз.

Прикладные операции находятся в `src/crm.ts`. Запись CRM, `order_events`, `admin_audit` и outbox выполняются одной транзакцией. Снимок стоимости заказа не меняется. Текст заметки, название задачи и контакты не включаются в аудит/outbox: события содержат идентификаторы и технические сведения об изменении. Публичный статус не раскрывает CRM.

При повторной отправке заметки или задачи нужно повторить UUID `id` и исходное тело. Одинаковая операция того же автора возвращает `replayed: true`; другое тело, автор или заявка — `409 IDEMPOTENCY_CONFLICT`. Браузер держит этот UUID на форме до успешного сохранения или закрытия карточки; после перезагрузки страницы автоматического восстановления операции нет. Изменения назначения и состояния задачи защищены версией, устаревшая правка возвращает `409 VERSION_CONFLICT`.

## Запуск и проверка

После обновления кода перезапустите локальный сервер обычным способом: в development он применит миграцию. Откройте `/admin/` и выберите CRM. Для production миграция выполняется отдельно через `pnpm db:migrate` до запуска новой версии; в этой задаче production не изменялся.

Проверены `pnpm check` и `pnpm test`: 23 теста проходят на PGlite, включая 6 новых CRM-тестов. Проверки охватывают роли и отзыв доступа, Origin, конфликты версий, фильтры, календарь, дубли, текст вне аудита/outbox, пагинацию и полный откат при ошибке outbox. Реальный сервер PostgreSQL и конкурентный инвентарь не тестировались: инвентарь не менялся.

Браузерная проверка на изолированном сервере с БД в памяти: вход, открытие CRM, назначение ответственного, создание/завершение задачи, заметка с буквальным HTML-текстом, сохранность черновика заметки при добавлении задачи, перезагрузка, фильтры «Мои»/«Без ответственного», смена статуса и перемещение карточки. Реальные контакты и рабочая БД не использовались. Отдельная проверка мобильного размера не выполнялась.

Для повторения есть `scripts/crm-browser-server.ts`: задайте временный `CRM_BROWSER_PASSWORD` через окружение и запустите `node --import tsx scripts/crm-browser-server.ts`. Сервер слушает только `127.0.0.1:4182`, логин — `crm-browser`, база исчезает при остановке. Скрипт не записывает пароль в файлы или логи и не запускается обычным `pnpm start`.

## Следующий гостиничный этап

Нужны фактические домики/комнаты/места, вместимость, правила размещения и утверждённые тарифы. После этого можно спроектировать шахматку и подтверждение с транзакционным контролем доступности и тестами на настоящем PostgreSQL. Оплата, синхронизация OTA, уведомления, миграционный учёт и интеграция с выбранным поставщиком — отдельные работы. Outbox пока сохраняет события, но никому их не отправляет.
