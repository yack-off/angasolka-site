## Как выполнять будущие запросы «протестируй»

1. Прочитать этот файл, README проекта, архитектуру и актуальные исходники затронутого сценария. Проверить изменения рабочего дерева. Старые отчёты не доказывают работоспособность текущей версии.
2. Если область не уточнена, выполнить smoke всех трёх разделов: все P0 из таблиц. Затем релевантные P1 изменённых модулей. Запрос «полный регресс» означает все P0/P1/P2; недоступные проверки отметить BLOCKED, будущие функции — N/A.
3. Подготовить изолированную среду по test-data.md. Проверки интерфейса выполнять в браузере, проверки прав — также прямыми API-запросами. Каждый вариант параметризованного кейса отмечать отдельно.
4. Для backend выполнить `pnpm check` и релевантные автоматические тесты; для полного регресса — `pnpm test`. Примеры выбора: `pnpm exec tsx --test tests/api.test.ts`, `pnpm exec tsx --test tests/admin.test.ts tests/crm.test.ts`. Рабочий каталог — корень проекта. Проверки Telegram использовать с подставным транспортом, без реальной отправки.
5. Создать новый `runs/YYYY-MM-DD-HHMM-<scope>.md` по шаблону; указать часовой пояс времени запуска, версию/состояние рабочего дерева, фактическую среду, команды и доказательства. В исходных чек-листах не хранить результаты отдельных запусков.
6. Сообщить пройденное, дефекты, блокеры и непроверенное отдельно. Невыполненный кейс нельзя считать успешным. FAIL содержит шаги воспроизведения и ожидаемый/фактический результат. Исправления приложения выходят за рамки составления этих документов.

## Обозначения

- **P0** — критический путь, защита доступа и целостность данных; smoke перед передачей версии.
- **P1** — основной регресс, ошибки и границы.
- **P2** — расширенная совместимость и удобство.
- **PASS / FAIL / BLOCKED / NOT RUN / N/A** — прошёл / дефект / не выполнен из-за блокера / ещё не запускался / неприменим с объяснением.
- В таблицах указаны предусловия, действия и проверяемый результат. Общие предусловия и обозначения данных находятся в test-data.md.

Наличие похожего автотеста не заменяет шаги кейса, браузерный путь и проверку дополнительных граничных вариантов. Проверки PGlite не подтверждают корректность конкурентных операций на серверном PostgreSQL. `TEST_DATABASE_URL` сейчас используется в `tests/api.test.ts`; остальные наборы и фактический драйвер проверять по коду перед запуском.

## Границы

Сейчас сохраняется заявка, а не подтверждённая бронь. Нет реального инвентаря, платежей, внешней CRM, автоматического восстановления секретного кода и объединения гостей по телефону. Не ждать от системы этих функций и не отмечать их отсутствие дефектом. После реализации нужны отдельные кейсы: конкурентная бронь последнего места на PostgreSQL; платёжные webhook, подпись, сумма и дубли; возвраты; внешние идентичности и синхронизация CRM.

Реальная отправка Telegram, публикация, production-миграции и платежи не входят в обычный локальный прогон. Утверждение тарифов и юридических текстов владельцем не заменяется техническими тестами.
