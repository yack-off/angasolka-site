# Telegram: заявки и уведомления

Реализован адаптер Telegram к общей базе заявок. Он выключен по умолчанию. Для отдельного тестового запуска через туннель 21 сентября 2026 подключён бот владельца и зарегистрирован HTTPS webhook. Владелец подтвердил ответ на `/start` и получение уведомления о заявке сайта. Настройка бесплатного демо и результаты проверки — [demo.md](demo.md).

## Сценарий гостя

1. Открыть бота и отправить `/start`, затем `/new`.
2. Ввести заезд, выезд, число мест и при необходимости услуги: `2027-06-10 2027-06-12 2 food=4 bath=1`. Заменить даты на будущие. Бот показывает актуальные коды услуг из каталога; даты считаются по Иркутску.
3. Последовательно ввести имя, телефон и пожелания. Телефон служит контактом, а не авторизацией.
4. Проверить состав, скидку, сумму и согласие. Нажать «Отправить заявку». При изменении тарифов потребуется новое подтверждение.
5. `/my` показывает последние 20 подключённых заявок с номером, статусом и суммой. Уведомления приходят при создании и изменениях заявки.

Для заявки с сайта: `/link КОД`, где КОД — секретный код из сохранённого подтверждения. Он передаётся сообщением в приватный чат, не в ссылке. Бот не сохраняет исходный update или код в БД; сообщение с кодом остаётся в Telegram, его можно удалить вручную. Это привязка только к минимальному статусу, без доступа к контактам, изменениям и отмене заявки. Заявка может быть подключена к одному Telegram-пользователю. `/stop` удаляет все подписки пользователя и черновик, а также ещё не взятые на доставку уведомления. Сами заявки и уже отправленные сообщения сохраняются. `/cancel` удаляет только черновик. Черновик истекает через час.

## Сценарий сотрудника

В текущей версии поддержан один сотрудник-получатель, явно связанный настройкой с действующим аккаунтом owner/manager в CRM. Ему приходят номер, текущий статус, даты, количество мест, сумма, источник и кнопки:

- «Принять в работу» переводит pending в contacted через общую операцию кабинета, с проверкой прав, версии, аудитом и outbox в одной транзакции.
- «Открыть кабинет» ведёт в `/admin/`, где нужны обычные учётные данные; там доступны контакты и полная карточка. Кнопка открывает кабинет, конкретную заявку выбирают по номеру из уведомления.
- «Написать гостю» появляется после подключения гостя к боту. Доступность перехода `tg://user?id=…` зависит от настроек Telegram. Для гостя только с сайта без подключения в Telegram остаётся контакт из карточки; искать аккаунт по телефону бот не пытается.

`/admin` показывает последние 20 активных заявок. Устаревшая кнопка не перезаписывает новую версию — нужно обновить список. Отключение сотрудника или перевод в viewer лишает его действий и блокирует ещё не отправленные административные уведомления. Один уже выполняющийся сетевой запрос отозвать нельзя.

«В работе» не означает подтверждённую бронь. Учёта свободных мест ещё нет, поэтому `confirmed` намеренно не добавлен. Полное подтверждение брони требует отдельного сценария инвентаря и правил размещения.

## Подключение владельцем

1. Создать бота в официальном BotFather. Токен сохранить в серверном `.env` или менеджере секретов; не отправлять его в переписку, git и логи.
2. Подготовить публичный HTTPS-сервер и PostgreSQL по README и `tls-russia.md`. Telegram должен доверять сертификату сервера; сертификат, доверенный только локально, не гарантирует работу webhook.
3. Создать аккаунт сотрудника в CRM. Его UUID доступен владельцу через существующий API сотрудников. Узнать числовой Telegram user ID из доверенного источника; username и телефон для этой настройки не подходят.
4. Заполнить `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` (случайная строка 32–256 символов A–Z/a–z/0–9/_/-), `TELEGRAM_ADMIN_USER_ID`, `TELEGRAM_STAFF_ID`, `PUBLIC_ORIGIN`. Только когда готова реальная отправка, установить `TELEGRAM_ENABLED=true`.
5. Выполнить `pnpm db:migrate` явно в production и запустить сервер. Миграция 004 создаёт таблицы Telegram. При включении worker начнёт обрабатывать также накопленные события — старые заявки могут породить несколько уведомлений с их текущим состоянием.
6. Отдельно выполнить `pnpm telegram:setup`. Это реальный внешний вызов `setWebhook`, который заменяет webhook этого бота. Команда задаёт секрет, `allowed_updates` и `max_connections=1` для последовательного диалога, не удаляет ожидающие обновления. Локальная разработка эту команду не запускает.
7. Сотруднику и гостю открыть бота и отправить `/start`. Проверить реальную тестовую заявку, уведомление, принятие в работу и переход в чат.

Чтобы выключить интеграцию, убрать `TELEGRAM_ENABLED=true` и перезапустить сервер. Маршрут webhook при этом не регистрируется и worker не запускается; Telegram может сохранять и повторять недоставленные updates до повторного включения. При окончательном отключении удалить webhook отдельно через Bot API.

## API и доставка

`POST /api/v1/telegram/webhook` доступен только при настройке Telegram. Проверяется `X-Telegram-Bot-Api-Secret-Token`, затем JSON Schema. Группы, сообщения ботов и несовпадение отправителя с приватным чатом игнорируются. OpenAPI содержит маршрут и схему авторизации. Публичные `/api/v1/orders` по-прежнему не принимают `source`, роль, статус или Telegram ID.

Webhook атомарно сохраняет receipt `update_id`, изменения заявки, диалог и исходящие ответы. Создание вызывает `createOrder` с серверным каналом `bot`; сайт продолжает использовать ту же операцию. Ошибка цены откатывает создание, после чего формируется новый расчёт. Нажатие старой кнопки не создаёт вторую заявку.

Worker каждые 2 секунды обрабатывает события `order.created`/`order.updated` из общей outbox. Поэтому любой будущий канал, использующий эти общие операции, получит тот же механизм уведомлений; сторонние сайты и CRM сами по себе ещё не подключены. Открытие страницы или незавершённый черновик уведомление о заявке не создают.

Таблица `telegram_events` хранит receipt отдельного потребителя, исходная outbox сохраняется для других интеграций. Очередь использует `FOR UPDATE SKIP LOCKED`, lease на минуту и до 10 попыток с задержкой от 30 секунд до часа. Доставка как минимум однократная: при успешной отправке и сбое записи результата возможен повтор. `delivered_at` означает успешный ответ Telegram, а не прочтение гостем. Для событий показывается текущее состояние заявки на момент постановки сообщения в очередь.

Ошибки доставки хранят только `SEND_FAILED`; токены, контакты и ответы API не логируются. Исходящая очередь содержит приватный текст подтверждения, доступ к БД должен быть ограничен. Доставленные тела очищаются через 7 дней, черновики — после истечения часа при следующем цикле worker. Неотправленные сообщения сохраняются для разбора. При остановленном worker автоматическая очистка не выполняется.

Оператор проверяет ошибки параметризованным запросом `SELECT id, attempts, error_code, available_at FROM telegram_deliveries WHERE delivered_at IS NULL AND error_code IS NOT NULL`. После устранения причины вручную повторяет конкретную доставку: `UPDATE telegram_deliveries SET attempts=0, available_at=now(), lease_id=NULL WHERE id=$1 AND delivered_at IS NULL AND attempts>=10`. Не сбрасывать активные lease массово. Отдельного интерфейса мониторинга очереди пока нет.

## Будущая оплата

QR и приём денег сейчас не реализованы. Предлагаемый следующий сценарий: подтверждённый заказ → сервер создаёт платёжную сессию на зафиксированную сумму → бот отправляет ссылку и QR на страницу оплаты этого заказа → гость выбирает доступный способ оплаты. Провайдер и способы ещё не выбраны; перечень не обещается заранее.

Платёжная ссылка должна иметь отдельный ограниченный по времени секрет, без контактов и кода статуса в URL. Оплата подтверждается проверенным webhook провайдера, с проверкой подписи, суммы, валюты, получателя и дедупликацией события. Сканирование QR, сообщение гостя и возврат со страницы оплаты не означают поступление денег.

## Проверки и границы

Локальные тесты используют PGlite и подменённую отправку. Проверяются диалог, согласие перед созданием, смена цены, идемпотентность, приватность, привязка по коду, права и версия, outbox, retry и отключение подписки. В демо 21 сентября 2026 проверены настоящий HTTPS webhook, ответ на `/start`, уведомление о заявке сайта и принятие в работу из Telegram с проверкой результата в CRM. Полный живой гостевой диалог, привязка по коду, переходы в чат и конкурентная работа нескольких worker на отдельном PostgreSQL ещё требуют проверки. Инвентарь в этой задаче не менялся.

Официальный контракт: [Telegram Bot API](https://core.telegram.org/bots/api), в частности `setWebhook`, `sendMessage`, `answerCallbackQuery` и `InlineKeyboardButton`.
