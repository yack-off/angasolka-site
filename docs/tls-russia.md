# HTTPS и сертификаты Минцифры

## Результат проверки

До этой правки сервер слушал только HTTP, TLS-файлы не загружались, конфигурации reverse proxy не было. Фронтенд обращается к своему origin относительными адресами: смена HTTP на HTTPS не требует переписывания форм. Админка уже устанавливает Secure cookie при HTTPS PUBLIC_ORIGIN.

Теперь предусмотрены два режима: TLS непосредственно в Fastify и HTTPS на Nginx с HTTP только по loopback до приложения. Поддержка относится к обычным X.509 PEM-сертификатам с алгоритмами RSA/ECDSA, поддерживаемыми Node/OpenSSL, в том числе выданным НУЦ Минцифры. Это не реализация ГОСТ TLS или электронной подписи. Конкретный сертификат Минцифры для домена не предоставлен и не выпущен в ходе разработки.

## Рекомендуемое размещение: Nginx → приложение

1. Получить сертификат для своего домена через официальный процесс [Госуслуг](https://www.gosuslugi.ru/tls). Право получения и требования к заявителю проверять там; тестовый самоподписанный сертификат не является сертификатом Минцифры.
2. На сервере разместить `fullchain.pem` (сертификат домена первым, далее выпускающие промежуточные сертификаты) и `privkey.pem` вне папки сайта. Корневой сертификат обычно не отправляется сервером. Ограничить чтение закрытого ключа учётной записью TLS-сервиса. Ключ не передавать в чат, Git или `public/`.
3. Скопировать `deploy/nginx/angasolka.conf.example` в конфигурацию Nginx и заменить все `YOUR_DOMAIN.example` реальным доменом, при необходимости в punycode. Шаблон рассчитан на один Nginx, принимающий соединения напрямую, без CDN/LB перед ним.
4. Настроить окружение приложения:

```dotenv
NODE_ENV=production
HOST=127.0.0.1
PORT=4180
PUBLIC_ORIGIN=https://YOUR_DOMAIN.example
TRUST_PROXY=loopback
# DATABASE_URL и ADMIN_SESSION_KEY также обязательны, см. README.
# TLS_CERT_FILE/TLS_KEY_FILE в этом режиме у приложения не задавать.
```

5. Выполнить миграции, запустить приложение, проверить `nginx -t`, затем применить конфигурацию Nginx. Открыть только 80/443; порт 4180 и БД не публиковать. Nginx перезаписывает входящие X-Forwarded-* вместо доверия к присланным клиентом значениям. Приложение доверяет только loopback, поэтому IP-лимиты работают по адресу посетителя. Для контейнеров/другой сетевой схемы нужна отдельная настройка доверенных адресов.

Шаблон не применён автоматически: домен, сервер и настоящий сертификат пока не заданы. `nginx -t` на этой Windows-машине не выполнялся — Nginx не установлен.

## Прямой HTTPS без Nginx

```dotenv
HOST=127.0.0.1
PORT=4443
PUBLIC_ORIGIN=https://YOUR_DOMAIN.example:4443
TLS_CERT_FILE=/etc/angasolka/tls/fullchain.pem
TLS_KEY_FILE=/etc/angasolka/tls/privkey.pem
TRUST_PROXY=none
```

```sh
pnpm tls:check
pnpm start
```

`tls:check` проверяет формат PEM, срок действия включённых сертификатов, SAN домена, соответствие ключа, порядок и подписи представленных промежуточных сертификатов и возможность загрузки в OpenSSL. Он не проверяет отзыв, наличие отсутствующего промежуточного сертификата или доверие конкретного браузера. Проверку цепочки до выбранного доверенного корня выполнять отдельно при вводе в эксплуатацию. Ошибка конфигурации прекращает запуск — автоматического отката на HTTP нет. Минимальная версия TLS — 1.2, также доступна 1.3. В HTTP-режиме локальная разработка продолжает работать.

После замены файлов прямой Node-сервер нужно перезапустить; Nginx — проверить и reload. Проверять срок заранее, например за 30 дней. Мониторинг и автоматическое продление в этом этапе не подключены.

## Браузеры российских посетителей

Национальный УЦ и география аудитории не гарантируют доверие всех браузеров. [Яндекс описывает поддержку сертификатов НУЦ](https://browser.yandex.ru/b/certificate); для остальных браузеров/ОС потребуется проверка реального домена и текущего хранилища доверия. [ГИС ЖКХ публикует инструкцию по сертификатам Минцифры](https://cdn.dom.gosuslugi.ru/webhelp/topics/login/administrative_body/t_add_main_certs-reg.html).

Сайт не может установить доверенный корень посетителю или исправить ошибку TLS своим JavaScript: TLS проверяется до загрузки страницы. Не предлагать обход предупреждений или передачу заявок по HTTP. Смена УЦ в конфигурации сервера не требует изменений бизнес-логики. Для максимального охвата проверить целевые версии Яндекс Браузера, Chrome, Safari/iOS, Firefox и Android на реальном домене; при необходимости выбрать подходящий сертификат с более широким доверием. Два сертификата на одном домене не дают автоматического выбора по хранилищу доверия клиента.

## Исходящие соединения и БД

Серверный сертификат сайта не добавляет доверия к другим сайтам. Когда появится интеграция с API под НУЦ, при необходимости можно передать официальный PEM-bundle через `NODE_EXTRA_CA_CERTS` **до старта Node** (окружение службы). Запись только в `.env`, загружаемый приложением уже после старта, для этой переменной не подходит. Не применять `NODE_TLS_REJECT_UNAUTHORIZED=0` или `rejectUnauthorized:false`. Сейчас исходящие AI/платёжные вызовы не добавлены и доверенное хранилище ОС не менялось.

Тестовые CA и ключи генерируются на время тестов, не коммитятся и не устанавливаются в системное хранилище. TLS-тесты проверяют соединение с явным доверием CA, отказ без доверия, неверный домен/ключ/срок/цепочку, версии TLS 1.2/1.3, Secure cookie и доверенные заголовки прокси. Это проверка механизма интеграции, не сертификация и не проверка живого сертификата Минцифры.
