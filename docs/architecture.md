# Решения и развитие

## Почему модульный монолит

Одна Node.js-служба, PostgreSQL и обычный HTTP API достаточны для текущего сайта. Fastify даёт JSON Schema-валидацию, ограничения запросов и OpenAPI. TypeScript strict помогает согласовывать изменения контрактов. Отдельные `pricing`, `orders`, `db`, `contracts` позволяют будущим каналам вызывать одни прикладные операции. Микросервисы, брокер сообщений, векторная БД и отдельная AI-платформа сейчас не нужны.

SQL-миграции и параметризованные запросы выбраны из-за небольшого числа сущностей и важности явных транзакций. Локальный PGlite выполняет PostgreSQL SQL; adapter `pg` работает с отдельным сервером. API не знает, какой используется драйвер. SQL пока сосредоточен в модулях; при росте выделять репозитории по бизнес-модулям, без универсального CRUD над всеми таблицами.

## Инварианты

1. Клиент не назначает цену, скидку, источник, статус или права. Сервер валидирует полный JSON Schema и рассчитывает сумму.
2. Заезд включён, выезд исключён. Даты без времени, календарь Asia/Irkutsk. Количество мест — целое 0..20; количество услуги — 0..100; длительность 1..365 ночей.
3. Цена фиксируется снимком в заказе и позициях; поздняя правка каталога не переписывает историю.
4. Для будущего редактирования тарифов: в одной транзакции сначала блокировать `pricing_policy` `FOR UPDATE`, менять каталог и увеличивать `version`. Создание заявки держит `FOR SHARE` этой строки.
5. Создание заявки, клиент, позиции, аудит и outbox коммитятся вместе. Идемпотентность защищена уникальным ключом и блокировкой строки. Ошибка полностью откатывает операцию.
6. Телефон из формы не доказывает личность. Не объединять клиентов по непроверенному телефону. Будущая CRM сможет объединять дубли с аудитом и проверкой прав.
7. Токен статуса — capability на минимальный набор данных, не идентификация клиента и не разрешение на отмену/изменение заказа.

## Что добавлять дальше

**Админка:** серверная идентификация сотрудников (OIDC или проверенная библиотека сессий), роли owner/manager/read-only, проверки разрешений в прикладных операциях. Добавить просмотр заявок с пагинацией, явные переходы статусов, optimistic locking через `version`, аудит с реальным actor ID. Общий API-key администратора в браузере не использовать.

Первый административный контур реализован в `/admin/`: сессия хранит только случайный токен в HttpOnly/SameSite cookie, в БД хранится его хеш. Доступ к ценам и сотрудникам — только owner; manager редактирует контент, медиатеку и заявки; viewer читает. Загрузка изображений проходит через `sharp`, перекодируется в WebP и очищается от метаданных. Контент хранится как типизированные поля в `content_blocks`; HTML из редактора не принимается. Действия пишутся в `admin_audit`, изменения заявки добавляют `order.updated` в outbox.

**Настоящее бронирование:** получить список домиков, комнат и койко-мест, ограничения размещения и расписания услуг. Добавить дневные остатки или интервалы на конкретные места; блокировать соответствующий инвентарь в транзакции, проверять доступность и только затем подтверждать. Обязательны конкурентные тесты на реальном PostgreSQL: две одновременные брони последнего места. До этого API намеренно не умеет выставлять `confirmed`.

**CRM:** первый сценарий обработки заявки реализован в `src/crm.ts` и `/admin/` (миграция 003). Общие `orders.status` и `orders.version`, ответственный, внутренние заметки, задачи с исполнителем и сроком по Asia/Irkutsk, фильтры и пагинация. Прикладные операции повторно проверяют права внутри транзакции, записывают событие/аудит/outbox вместе с изменением. Тексты заметок и задач не помещаются в события. POST заметки/задачи дедуплицируется по UUID с проверкой автора и тела; назначения и статусы задач защищены версиями. Расчёт тарифов не копируется. Дальше — проверенные внешние идентичности и профиль гостя между заявками. [Сравнение систем, контракт и границы](crm.md).

**Outbox:** для Telegram реализован отдельный потребитель (миграция 004, `telegram-worker.ts`) с receipts событий, очередью, lease и retry. Исходная outbox сохраняется для других каналов; `delivered_at` исходной outbox не означает доставку Telegram. Для будущих каналов добавить worker с lease/`FOR UPDATE SKIP LOCKED`, retry/backoff, идемпотентностью обработчиков по event ID, учётом ошибок и ручным повтором. Доставка как минимум однократная, не обещать exactly-once. Автоматическая отправка Telegram включается только явной серверной настройкой. Подробности и ограничения — [telegram.md](telegram.md).

**Бот:** Telegram-адаптер реализован в `telegram.ts`: приватный webhook с секретом, диалог, подтверждение расчёта, подключение минимального статуса по коду сайта, staff ID из конфигурации и повторная проверка прав. Статус contacted изменяется через общую с кабинетом `updateOrder`. Живое подключение выполнено для отдельной тестовой БД через туннель; результаты проверки — [demo.md](demo.md). Общий принцип для следующих каналов: транспортный адаптер Telegram/другого канала → авторизация идентичности → те же quote/create/track use cases. `source='bot'` назначает доверенный серверный код. Будущая GPT-интеграция должна интерпретировать запрос, но не писать SQL, не придумывать тарифы, свободные места или статус оплаты. Перед созданием/изменением заказа бот показывает состав и сумму и получает подтверждение гостя. Перед просмотром чужих данных проверяет владение заявкой.

**Оплата:** отдельный платёжный модуль, подпись webhook, дедупликация ID события, проверка суммы/валюты/получателя. Статус оплаты не следует из браузерного redirect или ответа GPT.

## Эксплуатация

Тестовый запуск `src/demo.ts` собирает существующие модули в один процесс и использует отдельную постоянную PGlite-базу `data/demo/postgres`. Рабочая БД в публичный туннель не передаётся. Cloudflared направлен на loopback-прокси с нормализацией доверенных заголовков; публичный bootstrap владельца отключён. При явном включении Telegram после проверки HTTPS регистрируется webhook и запускается общий worker. Настройка и границы — [demo.md](demo.md).

HTTPS: реализованы прямой TLS (PEM, RSA/ECDSA, минимум TLS 1.2) и конфигурация Nginx на том же хосте. Национальный УЦ Минцифры поддерживается как издатель стандартного X.509-сертификата, а доверие клиента остаётся свойством браузера/ОС. Прямой сервер проверяет SAN, срок, ключ и представленную цепочку до старта. Для прокси разрешён только явный loopback; локальное создание владельца в этом режиме отключено. Публичный origin указывается точно, без пути, credentials и завершающего слеша. API и модель данных не менялись. Подробности и непроверенные части — [tls-russia.md](tls-russia.md).

Для production — отдельный PostgreSQL, управляемые секреты, TLS, миграции до запуска приложения, health/readiness, резервные копии и тест восстановления, согласованные сроки хранения и удаления персональных данных. Локальную папку PGlite копировать для резервирования только после остановки процесса. Не трактовать её как переносимый дамп серверного PostgreSQL. Производственный PostgreSQL проверять отдельным CI job через TEST_DATABASE_URL. В текущей среде проверена PGlite-ветка; внешняя БД здесь не установлена.

Источники решений: [Fastify schemas](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/), [PGlite local development](https://pglite.dev/docs/about), [PGlite storage](https://pglite.dev/docs/filesystems).
